# Instructions for AI assistants working on EDCH

Read this file before changing anything. It lists the project's rules, what you must never do, and
how to add a feature. The details live in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) (code
organisation), [CONTRIBUTING.md](CONTRIBUTING.md) (conventions, releases) and
[docs/TRANSLATING.md](docs/TRANSLATING.md) (texts): read them too. When this file and your habits
disagree, this file wins.

EDCH (Elite Dangerous Companion Helper) is a Tauri v2 desktop app (Windows, Linux, Steam Deck,
ARM) with a framework-free TypeScript front end (`src/`) and a small Rust backend (`src-tauri/`).
It reads the game's journal and helps the player: materials, engineering, navigation, missions,
mining, colonisation, Powerplay, Thargoids, data sharing with EDDN, EDSM and Inara.

## Before you finish: the checks

```bash
npm install
npm test          # build + Prettier + layer check + translation check + unit tests
npm run format    # fixes formatting (Prettier, printWidth 120)
cargo fmt --manifest-path src-tauri/Cargo.toml     # Rust changes only
```

`npm test` must pass, with no exception. Never weaken a check to make it pass:
no `continue-on-error`, no skipped tests, no lint rule turned off, no file added to an ignore
list. If Prettier complains, run `npm run format`.

## Never

- **Never touch the game.** EDCH reads the journal and the companion files (`Status.json`,
  `Cargo.json`, `Market.json`…). It does not read or change the game's code or data, send inputs to
  the game or automate it. The option files (key bindings, graphics) are only exported and imported
  at the user's request, with a backup first; EDCH writes a binding file only for its own presets
  (`…_EDCH`), never the game's. The one exception in the game's installation folder: the default
  control presets (`ControlSchemes\*.binds`), read-only, nothing else (the READMEs say so).
- **No local database** (SQLite, IndexedDB…) and no new storage system. State is rebuilt from the
  journal; settings go through `state/store.ts` (saved in `localStorage` by the store). Small
  per-feature keys are fine when they follow the existing pattern (`edch.<name>`).
- **No new dependency** (npm or Cargo) without the maintainer's agreement. The front end has none at
  run time except the vendored i18next.
- **No private data in logs or anywhere it can leave the PC**: API keys, the remote access secret
  or QR code, the wing code, the Windows user name or home path, full IP addresses, the Wi-Fi name,
  typed text. Log through `platform/logger.ts` (front end) and `logs.rs` (backend), which redact;
  never `console.log` / `println!`.
- **No hard-coded user-facing text.** Every text shown goes through `t("namespace.key")` with the
  key in all six `public/locales/<lang>.json` files (en, fr, de, es, pt, ru). This includes menu
  labels, buttons, tooltips, errors and notifications.
- **No version numbers in code**: no `// FEATURE-v1.4` markers, no `foo-v152.test.mjs` file names,
  no versioned storage keys, no change to the window title. Git keeps the history; comments
  explain the code.
- **No personal or build files in the repository**: archives, generated patches, notes about your
  own machine, publication scripts, local screenshots, extra CI workflows. CI is
  `.github/workflows/build.yml` only.
- **No Windows pop-ups** (message boxes, native dialogs): use the app's own dialogs (`ui/dialog.ts`),
  banners and notifications.
- **No new network host, no change to the content security policy, no change to the wing or remote
  protocols** without the maintainer's agreement. Hosts the UI may reach are an allow-list in
  `src-tauri/src/http.rs`. Nothing may contact a server at start-up for users who didn't enable the
  feature.
- **Don't push to `main`, publish a release, rename release files or cancel builds.** Only the
  maintainer decides. Work on a `prerelease/<version>` branch (see Releases).

## Always

- **English in the code**: names, comments, logs, commit messages, CHANGELOG.
- **Readable, logical names.** `camelCase` variables and functions, `PascalCase` types and classes,
  `UPPER_SNAKE_CASE` module constants, `*_LABELS` for label maps. No abbreviations a newcomer
  can't guess.
- **Document everything**: a header comment at the top of every file (what it is for), a `/** … */`
  comment on exported functions, types and fields whose name doesn't say everything. Comments say
  why, not what the next line does.
- **Follow the existing architecture and naming**: look at how a similar feature is already done
  and do the same (see "Adding a feature"). Don't invent a parallel mechanism.
- **Official game names**: materials, modules, blueprints, ships, Thargoid types… use the names the
  game shows, in each language (`public/locales/game.<lang>.json`, generated by
  `tools/gen_game_locales.py`). Don't translate them yourself.
- **Translations follow each file's tone**: French uses "tu", Portuguese is Brazilian ("você",
  "compartilhar"), and so on. Read the neighbouring keys first.
- **Test what you change**: add or update tests in `test/<topic>.test.mjs` (a name that says what is
  tested). Tests import the built files from `dist/js/…`.
- **Keep changes small and focused**: one feature or fix per change. A change nobody can review in
  one sitting won't be merged.

## Architecture in short

Layers, lowest first. A module imports only from its own layer or lower ones
(`tools/check-layers.cjs` enforces it; `import type` is free):

`platform` < `game` < `state` < `ui` < `services` < `features` < `views` < `app`

| Layer | Holds | Rule |
| --- | --- | --- |
| `platform/` | Calls to Rust (`bridge.ts`), logger, i18n, version | The **only** place that calls Tauri. Never use `window.__TAURI__` elsewhere. |
| `game/` | Pure functions: journal events → state, game data | No DOM, no network. |
| `state/` | `store.ts`, settings types and defaults | Everything the app knows lives in the store. |
| `ui/` | `h()` DOM helper, dialogs, banners, notifier, menu | Shared display pieces. |
| `services/` | Other sites: Spansh, EDSM, EDDN, Inara, wing, remote server | Network code only. |
| `features/` | Logic behind the pages, without DOM pages | Calculations, matching, routes. |
| `views/` | One folder per page (`index.ts`), `shared/`, `detail/` | Draws from the store. |
| `app/` | Start-up and wiring: `main.ts`, `shell.ts`, `header.ts`, `journalFeed.ts` | Glue only. |

Data flows one way: journal → `app/journalFeed.ts` → `game/journal` (commander state) and
`game/activity` (what outlives a session) → `state/store.ts` → the shown page's `update()`.
Pages don't talk to each other through `window` events: they read the store.

The Rust backend moves bytes (files, HTTP, local server); it never interprets game data. Errors
the user can see are returned as codes and translated by the UI (`backend.<code>` keys).

## Adding a feature

1. **Find the closest existing feature and copy its shape.** Examples: the Thargoids page
   (`game/activity/thargoids.ts` + `views/thargoids/`), Powerplay, Mining, the share mode
   (`services/sync/shareMode.ts` + `views/shared/shareModeSwitch.ts`).
2. **Journal data** goes in a domain file of `src/game/activity/` (or `game/journal/` for the
   commander's current state): export a `<DOMAIN>_EVENTS` handler map, add it to `mergeHandlers()`
   in `game/activity/index.ts`, and the state's type and default to `game/activity/state.ts`. Add
   the event names to `HISTORY_EVENTS` when the history must be replayed at start-up, so the page
   is right after a restart (EDCH replays the journals, it doesn't store its own copy).
3. **Settings** go in `state/` (a typed `…Settings` interface with a `DEFAULT_…` and a doc comment
   per field), merged in `store.ts` like the others so older saved settings keep working.
4. **Logic** without DOM goes in `features/<topic>/`; **network** in `services/`.
5. **A page**: `views/<page>/index.ts` with a class implementing `View` (`mount`, `update`), added to
   `createViews()` in `app/shell.ts` and to `NAV` and `DEFAULT_ORDER` in `ui/menu/pages.ts`, in
   the group it belongs to (next to related pages), with a translated label (`nav.<page>`).
6. **Texts**: keys in the six locale files (`npm test` reports missing or unused ones).
7. **Styles**: in `public/styles.css`, at the end of the section the page belongs to, using the
   theme's CSS variables and the shared `button.primary` / `button.ghost` styles.
8. **Rust command** (only if the web page can't do it): a module in `src-tauri/src/`, registered in
   `lib.rs`, called through a wrapper in `platform/bridge.ts`, platform differences behind
   `#[cfg(target_os = "…")]`.
9. **Tests** in `test/`, a line in `CHANGELOG.md` under the version being prepared, then `npm test`.

## Releases

- Version bumps stay in `0.10.x` unless the maintainer says otherwise (then update this line). The version is in
  `package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `src/platform/version.ts`,
  `test/v02.test.mjs` and the READMEs' release example.
- Every user-visible change gets a line at the top of `CHANGELOG.md` (English): that section becomes
  the release notes and the update banner.
- A push to `prerelease/<version>` publishes a pre-release (`v<version>-pre.<run>`). Releases are
  published from `main` by the maintainer only (commit containing `[release]`).

## Keeping this file current

This file is part of the project and must stay true. Update it in the same change when:

- the version changes series (`0.10.x` → `0.11.x`, …): the version line above, and every rule the
  new series changes;
- a convention, a rule or the architecture changes (new layer, new storage, new check, new CI step,
  a new place for something);
- a new feature becomes the best example of a pattern ("Adding a feature", step 1).

Also check it against the code at every release: paths, file names and commands it mentions must
exist.
